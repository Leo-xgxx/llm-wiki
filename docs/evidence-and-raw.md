# Evidence and the raw layer

`raw/` holds managed evidence snapshots, not platform dumps. The one criterion for anything under it: **could a reviewer reproduce or check a card's claim from this file, without access to the live system?** If the answer is no, the file does not belong.

## KEEP / DELETE

| KEEP (carriers of a definition's truth) | DELETE (dumps, probes, noise) |
|---|---|
| a view or report definition: filters, grouping, date axis | query results, row samples, exports |
| an interface schema: fields, types, declared value domains | full dependency graphs that can be queried on demand |
| a document that states a rule, captured once with provenance | repeated captures of the same document |
| a dated observation recorded as a pattern ("queries without a refund filter dip then stay low") | the numbers behind the observation |
| an owner's explicit decision, as a registry contract | chat transcripts around the decision |
| | probe output, error messages, retry logs |
| | signed or expiring URLs, download links, session tokens |
| | anything generated by the build |

Deletion is a first-class outcome of review: a file that was useful during mining and is no longer a carrier of any card's truth is removed, not annotated.

## Provenance header

Every source-registry contract carries a complete provenance block, including semantic decisions and observed-output contracts as well as snapshots:

- `origin`: a stable logical pointer to where it came from. In a public design repository this is a description; in a private deployment it may be a link, but never a signed one.
- `captured_on`: the capture date.
- `state_at_capture`: exactly one of `live`, `archived`, `draft`, `published`, `approved`, or `unknown`.
- `trust`: `authoritative`, `second-hand`, or `low`.

A contract without provenance cannot be reviewed. The validator rejects every registry contract missing any of these four fields; evidence kind does not create an exception. When a value-domain card records `captured_on`, that date must equal the provenance date of its source contract.

`provenance.captured_on` describes the registry's current capture, not the first date the source ever existed. Re-capturing a stable contract may move that date forward. Every active card must then be reviewed against that current capture, so its ordering is `provenance.captured_on <= evidence.checked_at <= freshness.last_verified`. A deprecated card preserves a historical review act and may predate a later re-capture of the stable contract; it is not executable or answerable, so the validator does not reinterpret that historical date.

A `document-snapshot` contract also carries an `artifact` block:

```yaml
artifact:
  path: raw/snapshots/<slug>.md
  sha256: <64 lowercase hexadecimal characters>
```

The path names a non-empty UTF-8 Markdown snapshot managed under the domain's `raw/snapshots/`; the hash covers that file's bytes. A source card that references this contract must repeat the same capture date and trust in `snapshot.captured_on` and `snapshot.trust`; a mismatch is a failed evidence bridge, not a warning.

## Standard raw layout

```text
raw/
  source-contracts.yaml      the registry; every card reference resolves here
  snapshots/<slug>.md        managed document artifacts bound to registry path + SHA-256
  definitions/<slug>/        view and report definitions
  schemas/<slug>/            interface schemas
```

One stable artifact path per source, kept thin. Each path belongs to exactly one `document-snapshot` contract, and every managed snapshot under `raw/snapshots/` must be registered. No versions side by side: a re-capture replaces the file, updates its SHA-256, and bumps `captured_on`; the changelog records what changed.

## Lineage policy

- The **direct upstream** of a dataset or metric is recorded on the card (interface bridge, `depends_on`).
- The **full lineage** is queried live when needed. It changes too often to snapshot and is rarely needed to answer.
- A lineage claim that cannot be checked against an interface is written as "reported upstream" with its evidence level, not as fact.

## Probes, failures and time-limited proofs

- A probe that succeeded proves that the interface existed and responded on that date; record that fact in the evidence item, not the probe output.
- A probe that failed proves nothing about the knowledge; it goes into a runtime record, never into `raw/` or a card.
- Time-limited proofs (a signed link, a temporary export) are evidence only until they expire. Convert what they proved into a dated observation contract and delete the proof.
- "Empty output" is not "zero". An interface that returned nothing may be unavailable, filtered, or empty; the card records which of the three was established.

## The source card

A `source` card is the graph's bridge from a snapshot to knowledge. It has role `evidence`, points through `snapshot.registry_ref` to a `document-snapshot` registry contract, repeats that contract's `captured_on` and `trust`, and lists the canonical cards it supports in `index_to`. Its body records what was extracted, and what was deliberately not extracted — proposals, drafts and figures that are not knowledge yet. That second list is where the next gap record usually comes from.

## What never enters the repository

Restating the hard boundary because the raw layer is where it is most often broken:

- live credentials, identity mappings, session material;
- row-level production data, however small;
- complete machine dumps that can be queried on demand;
- transient failures and debug output;
- expiring or signed URLs;
- duplicate copies of the same source;
- generated runtime artifacts.
